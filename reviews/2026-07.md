## Top 5 Highest-Impact Improvements

### 1. Dashboard crashes with KeyError on scan result keys

**File:** `dashboard.py`
**Lines:** 303, 334, 340, 472–477, 577–584, 582–584
**Severity:** Critical — renders the dashboard unusable

**Issue:**  
The dashboard calls `scanner.evaluate_symbol()` to build the scan snapshot, then reads the result dict using keys `r["sma200"]` and `r["above_sma200"]`. However, `scanner.py` returns these values under the keys `"sma200_daily"` (line 194) and `"above_daily_sma200"` (line 195). This mismatch causes `KeyError` every time the Overview "📥 Entry Signals" section or the "Per-Ticker" tab renders — which is on every page load.

**Affected calls:**
```python
# dashboard.py:303
sma = r["sma200"]               # KeyError — should be r["sma200_daily"]

# dashboard.py:472
above = "✅ above" if r["above_sma200"] else "❌ below"   # KeyError

# dashboard.py:474
f"SMA(200) {r['sma200']} {above}"                         # KeyError

# dashboard.py:577
close_delta = "▲ above SMA" if r["above_sma200"] else "▼ below SMA"  # KeyError

# dashboard.py:582
sma_delta = "trend ✅" if r["above_sma200"] else ...      # KeyError
```

**Fix:** Replace all occurrences of `r["sma200"]` → `r["sma200_daily"]` and `r["above_sma200"]` → `r["above_daily_sma200"]` in `dashboard.py`. Five string replacements, no logic change.

**Expected impact:** Fixes a silent crash that currently makes the dashboard show a Streamlit error banner instead of signal data.

### 2. Fallback exit logs pre-fill price, not actual fill price

**File:** `executor.py`
**Lines:** 289–296
**Severity:** High — corrupts the P&L record for any trade that uses the fallback market sell

**Issue:**  
When a LOO sell expires unfilled, `confirm_exit_fills()` submits a fallback DAY market sell, then immediately calls `trade_log.log_closed_trade(pos_data, fallback_price, ...)` using `fallback_price = float(alpaca_positions[symbol].current_price or alpaca_positions[symbol].avg_entry_price)`. This is the **live quote at the moment the order is submitted**, not the price at which the fallback market order fills. For a DAY market order submitted at 9:45 AM, the fill typically arrives seconds later — but on a volatile open, the fill can be meaningfully different.

The SPY `time_stop_fallback` P&L of +$374.92 in trades.csv may be calculated from the pre-fill quote, not the actual fill price.

**Fix:**
```python
# executor.py — confirm_exit_fills(), after submitting fallback sell
# Don't log immediately. Instead, set exit_status = "exit_pending" and let the
# next confirm_exit_fills() cycle detect the position gone from Alpaca and
# look up the fill via get_last_fill_price(symbol, "sell") — the same flow
# used for LOO exits that do fill.
```
Concretely: remove lines 288–296 (the immediate log) and instead call `pt.mark_exit_pending(symbol, reason=log_reason)` after the fallback submit, just like is done for the LOO path. The existing `confirm_exit_fills()` loop at the top of the function already handles `exit_pending → fill confirmed → log` correctly.

**Expected impact:** Correct P&L for any trade that took the fallback path (~5–10 bps accuracy per trade; cumulative accuracy as these trades accumulate).

### 3. Time stop can be skipped entirely by a single day's scan failure

**File:** `main.py`, `position_tracker.py`
**Lines:** `main.py:102–207` (post_close_scan), `main.py:334–348` (error loop)
**Severity:** High — demonstrated by the July DNS crash; SPY held 14 days instead of 7

**Issue:**  
The time stop is evaluated only inside `post_close_scan()` at 16:30 ET. If that job throws (network outage, DNS crash, API timeout), the time stop is not queued. `main.py:334–348` retries the job on the next 30-second tick within the same scheduler loop, but the `schedule` library marks a job as "not run" when it raises — it will not fire again until the next scheduled time (the following trading day at 16:30). So a single scan failure delays any pending time stop by a full trading day. The July DNS crash delayed SPY's exit by 7 days.

**Fix:**  
Add a safety check at the top of `fill_confirm()` (09:45 ET — the second scheduled job, which typically succeeds even on bad scan days because it just talks to Alpaca):

```python
# main.py — add inside fill_confirm(), after _skip_if_closed check
# Emergency time-stop guard: catch any position that missed its scan-day exit
for sym in pt.get_time_stop_symbols():
    if sym in executor.get_alpaca_positions():
        logger.warning(f"⏰ Emergency time-stop: {sym} missed scan-day exit. Queuing now.")
        executor.submit_exit(sym, reason="time_stop_emergency",
                             close_price=float(executor.get_alpaca_positions()[sym].avg_entry_price))
```

`pt.get_time_stop_symbols()` already exists at `position_tracker.py:149`. The check adds one Alpaca call per day; at fill_confirm time the market is still open and the exit can be submitted with LOO + market fallback as usual.

**Expected impact:** Prevents time-stop overruns from scan-day failures. SPY's July outcome would have been caught on the next trading day's 09:45 confirm, not after a week.

### 4. `position_tracker.py` reads and writes the JSON file on every single operation

**File:** `position_tracker.py`
**Lines:** All public functions (e.g., `add:37`, `get:123`, `all_positions:127`, `time_stop_triggered:145`)
**Severity:** Medium — no data loss today, but a latent concurrency hazard

**Issue:**  
Every call to a public function opens `positions.json`, parses it, and (for mutations) writes it back — even when called back-to-back in the same confirm cycle. In `confirm_fills_and_place_stops()`, for each symbol the code calls `pt.all_positions()`, `pt.get()`, `pt.update_entry_price()`, and `pt.update_stop_order_id()` — four file-read-write cycles per position. With 5 positions, that is 20 disk operations in a tight loop with no atomic locking. On Windows (the production environment), this risks `PermissionError` if the bot and the dashboard's `position_tracker` calls overlap. There is also no `fcntl` locking or tempfile-rename pattern.

**Fix (minimal):**  
Pass a loaded `data` dict into the inner helpers instead of re-reading per call, or batch mutations:

```python
# position_tracker.py — replace all body calls in confirm_fills_and_place_stops
# with a single load → mutate → save:
data = pt._load()
data[symbol]["entry_price"] = fill_price
data[symbol]["stop_order_id"] = stop_order_id
pt._save(data)
```

Or, longer term, use `filelock` (already in Python ecosystem) and cache the loaded dict for the duration of a single scheduler job.

**Expected impact:** Eliminates intermittent `PermissionError` / corruption risk on Windows; ~3× fewer disk ops per confirm cycle.

### 5. Zero automated test coverage

**Files:** entire codebase — no `test_*.py` files exist

**Issue:**  
The codebase has no automated tests. ## Code Quality Notes

- **`dashboard.py:303` — `explain_decision()` bug (also covered in #1):** The local variable `sma` shadows Python's built-in `sma` import from `indicators`; rename to `sma200_val` after fixing the key name.
- **`position_tracker.py:68` — `datetime.utcnow()` deprecated:** Python 3.12+ warns on `datetime.utcnow()`; replace with `datetime.now(timezone.utc).isoformat()` (same pattern already used in `main.py:64`).
- **`trade_log.py:37-39` — `exit_date = date.today()`:** The exit date is stamped at the time `log_closed_trade()` is called, which is inside `confirm_exit_fills()` at 09:45 ET — the day after the signal fires. For hard stops detected in `post_close_scan()`, the exit date is actually the prior trading day (the stop triggered during the session). Both cases stamp `date.today()`, which is correct for LOO exits but may be off by one for hard stops detected at the 16:30 scan. Low impact on trades.csv accuracy, but worth noting.
- **`backtest.py:343` — RSI exit check uses `rsi2[i-2]`:** The live scanner compares `prev_rsi2` (index `i-1`) to the threshold, but `backtest.py:343` compares `rsi2[i-2]`. This is a two-day lag vs. the scanner's one-day lag — a subtle live-vs-backtest drift. The backtest RSI exit will fire one day later than the live bot would. Line 344 also correctly uses `prev_rsi` (`i-1`), so the check spans `i-2` and `i-1` in the backtest but `i-2` and `i-1` ... wait, in the live scanner it's `(prev_rsi2 >= 70) and (last_rsi2 < 70)` which compares yesterday and today; in the backtest it's `(rsi2[i-2] >= 70) and (prev_rsi < 70)` which compares two-days-ago to yesterday. Exit will trigger one bar earlier in the backtest than in the live bot. **Cite:** `scanner.py:129` vs. `backtest.py:343`. Medium impact on backtest accuracy.
- **`scanner.py:49` — data feed is IEX (free tier):** IEX has coverage gaps for low-volume tickers. All current symbols are highly liquid ETFs, so this is acceptable. But worth noting if the universe is ever expanded to include stocks (screener.py results).
- **`main.py:47` — `_pending: list[dict]` is a module-level mutable:** Cleared at the top of `post_close_scan()`. If two threads ever called `post_close_scan()` concurrently (e.g., from a future async refactor or a double-schedule bug), this would silently race. Mitigated by `pending.json` persistence, but the in-memory lock is a single global list. Not an active issue.
