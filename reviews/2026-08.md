## Top 5 Improvements

### 1. Position Size Not Recalculated After Actual Fill
**File:** `executor.py:85–86` (size estimate) and `executor.py:200–216` (stop calculation)  
**Issue:** `submit_entry()` calls `risk.calculate_position_size(equity, est_entry, active_stop)` where `est_entry` is yesterday's close. The actual LOO fill can be up to 0.5% higher (the `ENTRY_LIMIT_PCT` ceiling). If SPY closes at $739 and fills at $742.70, the stop distance shrinks from `$739 - stop` to `$742.70 - stop`, meaning the position is slightly over-risked relative to the 1% target. For the 2.5×ATR stop on liquid ETFs this is a small but systematic error.  
**Fix:** In `confirm_fills_and_place_stops()` (executor.py:132), after `fill_price = float(alpaca_pos.avg_entry_price)` is known, recalculate shares: `recalc_shares = risk.calculate_position_size(equity, fill_price, actual_stop)`. If `recalc_shares < shares`, submit a corrective sell for the difference before placing the stop. This fully closes the 1%-risk guarantee.  
**Expected impact:** Eliminates systematic over-sizing on LOO fills; negligible for most trades but matters when the entry limit is hit at exactly 0.5% above close.

---

### 2. Fallback Exit Logs P&L Before the Market Order Fills
**File:** `executor.py:278–296`  
**Issue:** When a LOO sell expires unfilled, a fallback DAY market sell is submitted (line 281), and then `trade_log.log_closed_trade(pos_data, fallback_price, ...)` is called immediately on line 292 using `alpaca_positions[symbol].current_price` as the exit price. A DAY market order fills at the next available ask, which can differ from `current_price` at the time of submission. The logged P&L may be incorrect.  
**Fix:** Do not call `log_closed_trade()` at the point of fallback submission. Instead, add the symbol to a `fallback_pending` set in position_tracker. On the next `confirm_exit_fills()` cycle, detect it has cleared Alpaca positions, fetch the actual fill price via `get_last_fill_price(symbol, "sell")`, and log with the real fill.  
**Expected impact:** Accurate P&L records; currently XLV's -$864.60 logged from the fallback sell flow may reflect the wrong price.

---

### 3. Hard-Stop P&L Falls Back to Estimated Stop Price, Not Actual Fill
**File:** `main.py:126–133`  
**Issue:** When a hard stop triggers, `get_last_fill_price(symbol, side="sell")` is called (line 128). If it returns `None` (API error, or the filled order is beyond the 10-order limit in `executor.py:305`), the code falls back to `pos_data["stop_price"]`. But `stop_price` in the tracker is the **estimated** stop from the scan (based on yesterday's close and ATR), while the actual GTC stop placed on exchange is recalculated from the actual fill in `confirm_fills_and_place_stops()` and is not written back to `positions.json`. The divergence matters when the actual fill differed from the estimate.  
**Fix:** (a) After placing the stop order in `confirm_fills_and_place_stops()`, call `pt.update_stop_price(symbol, actual_stop)` to persist the actual stop. Add `update_stop_price()` to `position_tracker.py`. (b) Increase the `limit=10` in `get_last_fill_price` (executor.py:305) to `limit=50` to reduce `None` returns.  
**Expected impact:** Eliminates silent P&L miscalculation for hard-stop trades; the XLV -$864.60 entry cannot currently be verified as accurate.

### 4. Stop Cancellation Uses Fragile String Match on Order Type
**File:** `executor.py:412`  
**Issue:** The fallback stop-cancellation loop at line 412 uses `"stop" in str(order.order_type).lower()` to identify stop orders. If Alpaca's SDK changes the string representation of `OrderType.STOP` (e.g., to `"OrderType.STOP"` vs `"stop"`), this silently stops working — the stop order is not cancelled, and both the GTC stop and the new exit LOO would be live simultaneously, causing a double-sell.  
**Fix:** Replace the string match with a direct enum comparison:
```python
from alpaca.trading.enums import OrderType
if order.order_type == OrderType.STOP:
```
This is SDK-version-stable and intent-clear.  
**Expected impact:** Eliminates a potential double-sell scenario (sells 2× the position) which would cause an unintended short and a margin call in a live account.

## Code Quality Notes

- **`position_tracker.py:20`** — `STATE_FILE = Path("positions.json")` is a relative path. If the bot is launched from outside its directory (e.g., `python /path/to/Alpacabot/main.py` from `/`), the state file is created in the wrong location. Use `Path(__file__).resolve().parent / "positions.json"` (same pattern used for `PENDING_FILE` in `main.py:49`).

- **`trade_log.py:62`** — `CSV_FILE = Path("trades.csv")` has the same relative-path issue as above.

- **Backfill rows missing indicator data** — Trades 1–4 have empty `rsi2_at_signal`, `atr14_at_signal`, etc. These fields are required to audit signal validity. Any future backfill should also write indicator values. Consider adding a backfill script that reconstructs indicator values from historical bars.

- **`scanner.py:49`** — `feed=DataFeed.IEX` is the free-tier feed. IEX has known gaps for some ETFs during low-volume periods (pre/post-market). For production, consider upgrading to `DataFeed.SIP` (requires a subscription) or validating that IEX data matches SIP for the 11-ETF universe.

- **`main.py:325`** — `schedule.every().day.at(config.SCAN_TIME).do(status_report)` runs `status_report()` at the same time as `post_close_scan()`. Both evaluate `eval_checkpoint.check_and_notify()` — only `status_report` does this, but it fires alongside the scan. If the scan is slow, the status report may log stale position data. Separating them by a few minutes would make the log cleaner.

- **Trade 5 RSI anomaly** — SPY entered at RSI(2) = 20.49 in June, which violates the current `RSI_ENTRY_THRESHOLD = 10.0`. Either the strategy was using a different threshold at the time, or this was manually entered. The commit history (`67fe9ed Re-align strategy to Larry Connors RSI(2)`) suggests parameters changed during the paper period. All pre-`67fe9ed` trades should be treated as a different strategy configuration.
