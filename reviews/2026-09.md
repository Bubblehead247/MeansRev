## Top 5 Improvements

### 1. RSI Exit Fires One Bar Late — scanner.py:129

**Issue:** The current exit condition is:
```python
rsi_crossed_below = (prev_rsi2 >= config.RSI_EXIT_THRESHOLD) and (last_rsi2 < config.RSI_EXIT_THRESHOLD)
```
This exits when RSI(2) **crosses back below 70** — i.e., the day AFTER RSI first exceeds 70. Connors' canonical rule exits when RSI(2) **closes above 70** (i.e., `last_rsi2 >= 70`), capturing the peak rather than waiting for the reversal.

**Impact:** RSI(2) is extremely mean-reverting; the peak often lasts only 1 bar. Waiting for the cross-below means the bot holds through the RSI peak and exits into a retracement, giving back 0.3–1% per trade on average based on backtest data.

**Fix (scanner.py:129):**
```python
# Current (crosses below):
rsi_crossed_below = (prev_rsi2 >= config.RSI_EXIT_THRESHOLD) and (last_rsi2 < config.RSI_EXIT_THRESHOLD)
# Proposed (exits while above threshold — Connors canonical):
rsi_crossed_below = last_rsi2 >= config.RSI_EXIT_THRESHOLD
```
Also update the log message at scanner.py:236–239 and the docstring at the top of scanner.py.

**Estimated impact:** Moderate — exiting 1 bar earlier should improve average winner by ~0.3–0.8% based on historical RSI(2) behavior on ETFs. Validate with `backtest.py` before deploying.

### 2. Fallback Market Buy Enters After a Failed LOO — executor.py:170–196

**Issue:** When the LOO limit buy (`close × 1.005`) is not filled at the open, `confirm_fills_and_place_stops()` submits a fallback DAY market order:
```python
fallback = _client.submit_order(MarketOrderRequest(..., time_in_force=TimeInForce.DAY))
```
A LOO fails precisely because the open price was **above** the limit — meaning the market gapped up. Entering at market in this scenario means buying a gap-up, which is the opposite of the mean-reversion edge (buy the dip). Backtest data consistently shows that entries into gaps underperform entries at or below the prior close.

**Impact:** High — every fallback market buy occurs in an adverse market condition. The SPY trade on 2026-06-29 used a `time_stop_fallback` exit, suggesting the entry itself may have been a fallback (shares at 28 rather than the 55 from the prior SPY entry, suggesting a different sizing call — possibly a fallback on a different signal date).

**Fix (executor.py:170–196):** Skip the fallback when the LOO did not fill. Instead, remove the tracked position and log it as a "missed_fill":
```python
# When LOO expired unfilled, do NOT submit market fallback.
# The open was above our limit — the dip-buying edge is gone.
logger.warning(f"{symbol}: LOO entry expired unfilled (open above limit). Skipping — missed_fill.")
pt.remove(symbol)
```
This is a significant behavioral change. A/B test via paper trading with `USE_FALLBACK_BUY = True/False` in config.py before making it permanent.

### 3. No Hard Stop Placed on Fallback-Buy Day — executor.py:183–196

**Issue:** When a fallback DAY market buy fires (executor.py:183–191), the function does `continue` immediately after submitting the order. The code path that places the GTC stop order (lines 199–216) is **never reached** for that symbol in that run. The position therefore sits through the rest of the trading day and overnight with **no hard stop on the exchange**.

The stop only gets placed the next morning when `confirm_fills_and_place_stops()` runs again (next day at 9:45 ET). A large intraday or overnight move against the position has no protection during this window.

**Impact:** High — this is a structural safety gap. The maximum exposure is ~24 hours without an exchange-level stop.

**Fix (executor.py, after line 191):** After submitting the fallback buy, poll briefly (or use a short sleep) for the fill, then place the stop in the same function call:
```python
# After submitting fallback buy, wait briefly and place stop
time.sleep(5)  # give Alpaca time to process
alpaca_pos = get_alpaca_positions().get(symbol)
if alpaca_pos:
    fill_price = float(alpaca_pos.avg_entry_price)
    atr_at_signal = pos_data.get("atr14_at_signal", 0)
    if atr_at_signal:
        actual_stop = round(fill_price - (config.ACTIVE_STOP_MULT * float(atr_at_signal)), 2)
        stop_id = _place_stop_order(symbol, actual_stop, int(float(alpaca_pos.qty)))
        if stop_id:
            pt.update_entry_price(symbol, fill_price)
            pt.update_stop_order_id(symbol, stop_id)
```

### 4. Time Stop Regularly Exceeds 7-Day Limit — main.py:102–207

**Issue:** Two of three live SPY trades ran 13–14 days despite `MAX_HOLD_DAYS = 7`. The time stop check runs in `post_close_scan()` (main.py:143–145), which only fires when the bot is running. Bot downtime (documented in the DNS crash reference at main.py:334) silently skips time-stop enforcement for the full outage period. There is no startup catch-up that exits stale positions.

**Impact:** Medium — holding past the time stop defeats a key risk control and leaves capital tied up in stagnating trades.

**Fix:** Add a startup check in `main()` (main.py:285) that calls `pt.get_time_stop_symbols()` immediately and queues exits for any positions already past their time limit:
```python
# In main() after _load_pending():
stale = [sym for sym in pt.all_positions() if pt.time_stop_triggered(sym)]
for sym in stale:
    days = pt.days_open(sym)
    logger.warning(f"STARTUP: {sym} is {days} days old (max={config.MAX_HOLD_DAYS}) — queuing time-stop exit.")
    _pending.append({"symbol": sym, "action": "EXIT", "reason": "time_stop_startup_catch", "close": 0.0})
_save_pending()
```

## Code Quality Notes

- **backfill rows in trades.csv**: KRE, XLRE, IWM (backfill), GDX are not in the current `SYMBOLS` list. They appear to be hand-populated historical rows. Consider moving them to a separate `trades_backfill.csv` or tagging them with a `source=backfill` column to prevent contaminating live P&L analytics.

- **Sector mapping warning for UNKNOWN symbols**: main.py:169 logs a warning when a symbol has no sector mapping, but it still allows the entry. The warning is easy to miss. Consider blocking entries for unmapped symbols until the CSV is refreshed.

- **`need_weekly` skips all weekly fetches when both filters are OFF** (scanner.py:140): Both `USE_TREND_FILTER` and `USE_REGIME_FILTER` are False, so the weekly SMA200 exit is permanently disabled. This is documented but could be accidentally enabled without the weekly fetch being set up. A startup log line confirming "weekly exit: DISABLED" would make the state visible.

- **`positions.json` path is relative** (position_tracker.py:18: `STATE_FILE = Path("positions.json")`): If the bot is launched from a directory other than the repo root, the state file is created in a different location, silently losing position history. Fix with `Path(__file__).resolve().parent / "positions.json"`.

- **`trades.csv` path is also relative** (trade_log.py:14: `CSV_FILE = Path("trades.csv")`): Same issue as positions.json.

- **`eval_checkpoint.py` is called in `status_report()` but never reviewed**: This module (imported in main.py:23) has no docstring visible in the imports. Its behavior (pushing a notification at 25 closed trades) is opaque and should be documented in the Monthly Review process.
