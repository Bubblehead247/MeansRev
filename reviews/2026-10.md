## Top 5 Highest-Impact Improvements

### 1. Add a daily health-check heartbeat (uptime monitoring)

**Issue:** There is no mechanism to detect if the bot has stopped running. The 3.5-month gap in `trades.csv` (July 15 → November 2) was invisible until this review. The ntfy.sh notifier (`notifier.py`) already exists but is only called on trades, errors, and signals — never as a heartbeat.

**File/line:** `main.py:323-325` (scheduler setup); `notifier.py` (notification dispatch)

**Proposed change:** Add a daily status notification in `status_report()` — one push per day that the bot is alive and running, summarizing open positions and scan results. Use a sub-topic (e.g. `MeansRevRSI-health`) that the user can mute but that fires regardless of trading activity.

```python
# In status_report() — add after the logger block:
notifier.send_status(positions=len(positions), equity=executor.get_equity())
```

**Expected impact:** Immediately detects unplanned downtime. If the user doesn't see a daily ping, the bot is down.

### 2. `position_tracker.py` uses a relative path for `positions.json`

**Issue:** `STATE_FILE = Path("positions.json")` (`position_tracker.py:18`) is relative to the process working directory, not the script directory. If the bot is started from any directory other than the project root, `positions.json` is written to the wrong place. The bot silently creates a fresh, empty tracker and opens positions it thinks are new while the real `positions.json` sits untouched elsewhere. This can cause duplicate entries, missed stops, and missed exits.

`trade_log.py` correctly uses `Path("trades.csv")` with the same vulnerability. `eval_checkpoint.py:27` correctly uses `Path(__file__).resolve().parent`.

**File/line:** `position_tracker.py:18`, `trade_log.py:11`

**Proposed change:**
```python
# position_tracker.py:18
STATE_FILE = Path(__file__).resolve().parent / "positions.json"

# trade_log.py:11
CSV_FILE = Path(__file__).resolve().parent / "trades.csv"
```

**Expected impact:** Eliminates an entire class of "bot started from the wrong directory" incidents. Low effort, high safety.

---

### 3. Add a startup time-stop sweep when the bot restarts after a crash

**Issue:** The 7-day time stop (`config.py:129`) is checked only inside `post_close_scan()` at 15:30 CT. If the bot is offline at that exact time — the July 6 DNS crash already demonstrated this — the time stop is missed for that day. A position doesn't risk being stuck indefinitely (the check will catch it the next trading day), but it can be delayed by a full market day. The July crash caused a 14-day hold instead of 7.

More critically, `_load_pending()` in `main.py:321` restores queued signals but performs no check for overdue positions. If the bot restarts after being offline for several days, it enters the trading loop without queuing exits for positions that exceeded `MAX_HOLD_DAYS` while it was down.

**File/line:** `main.py:321` (`_load_pending` call in `main()`), `main.py:143-145` (time-stop check)

**Proposed change:** After `_load_pending()`, add a startup sweep:

```python
def _startup_time_stop_sweep():
    """Queue exits for any positions that exceeded MAX_HOLD_DAYS while the bot was offline."""
    open_pos = executor.get_alpaca_positions()
    for symbol in pt.get_time_stop_symbols():
        if symbol in open_pos and not any(
            p["symbol"] == symbol and p["action"] == "EXIT" for p in _pending
        ):
            close_ref = float(open_pos[symbol].avg_entry_price)
            _pending.append({"symbol": symbol, "action": "EXIT",
                              "reason": "time_stop_startup", "close": close_ref})
            logger.warning(f"Startup sweep: queued time-stop EXIT for {symbol} "
                           f"({pt.days_open(symbol)} days open)")
```

**Expected impact:** Eliminates the "bot restarted after outage, overdue positions not caught until next 15:30 scan" failure mode.

### 4. Fallback market buy after LOO expiry lacks a price-staleness check

**Issue:** When a Limit-on-Open buy order expires unfilled (stock gapped up past the +0.5% limit), `confirm_fills_and_place_stops()` unconditionally submits a DAY market buy (`executor.py:177-191`). This defeats the purpose of the LOO limit, which exists to avoid paying too much at the open. A gap of >0.5% implies the market opened above the signal reference price; the entry thesis (RSI(2) < 10, stock is oversold relative to prior close) may no longer hold.

**File/line:** `executor.py:170-196`

**Proposed change:** Before submitting the fallback, fetch the current ask price and compare it to the signal reference price. Skip the fallback if price has moved beyond a threshold (e.g. 1.5% above prior close):

```python
# After "LOO expired unfilled" log:
current_positions = get_alpaca_positions()
# A simple staleness guard: check if Alpaca position already exists (double-check)
# and whether the signal price was too stale.
scan_close = pos_data.get("entry_price", 0.0)  # estimated entry at scan time
# Fetch current quote and skip if gapped too far
# (implementation: alpaca quote endpoint or snapshot)
gap_threshold = scan_close * (1 + config.ENTRY_LIMIT_PCT * 3)  # 1.5%
# If current_price > gap_threshold: log warning and pt.remove(symbol); continue
```

**Expected impact:** Avoids entering trades where the RSI(2) oversold edge has already partially reversed at the open. Also prevents paying 2-3% above the original thesis price, which can invalidate the stop geometry.

### 5. Sector `UNKNOWN` silently bypasses the per-sector concentration cap

**Issue:** When a symbol has no entry in `sectors.csv`, `sectors.sector_of(symbol)` returns `sectors.UNKNOWN`. In `main.py:168-169`, the code logs a warning but does not block the entry. This means all UNKNOWN-sector symbols share no per-sector cap — if three symbols are all UNKNOWN, all three can be entered simultaneously despite `MAX_PER_SECTOR = 2`.

During May 2026, GDX and KRE were both traded — GDX is a gold miner ETF and KRE is a regional banking ETF. Both are in the current config as… actually, neither is in `config.SYMBOLS` anymore, so this is moot for the current universe. But if the universe is ever expanded (e.g. adding `GLD` — already in the list — plus new symbols), any unmapped symbol bypasses the cap.

**File/line:** `main.py:168-169`

**Proposed change:**
```python
if cand_sector == sectors.UNKNOWN:
    logger.warning(f"  ⛔ Skipping ENTRY {symbol} — no sector mapping (run screener.py)")
    continue   # fail closed instead of fail open
```

**Expected impact:** Enforces the 5×1% = max 5% total risk cap rigorously. Low effort, prevents silent concentration creep when the universe evolves.

## Code Quality Notes

- **`sma200_weekly_at_signal` logged as `0.0` when `USE_TREND_FILTER = False`** (`executor.py:118`): The scanner returns `last_weekly_sma200 = 0.0` as a default when the weekly fetch is skipped. This is stored in `positions.json` and `trades.csv` and looks like a missing or zero value. It would be clearer to store `None` or the string `"N/A"` so reviewers don't mistake it for a genuine SMA200 of $0.
  
- **`confirmed_exit_fills()` uses `current_price` fallback for logging only, but no order confirmation** (`executor.py:290-294`): When a fallback market sell fires and the position is logged, `fallback_price` is taken from `alpaca_positions[symbol].current_price` rather than from the actual fill. The fill price could differ materially if the stock is moving. The P&L logged in `trades.csv` may be inaccurate for `*_fallback` exit-reason rows. The proper fix is to wait for the fill confirmation from Alpaca rather than using `current_price` as a proxy.

- **`backtest.py` uses both Alpaca (IEX) and yfinance** (`backtest.py:29`): The live scanner exclusively uses the Alpaca IEX feed, but `backtest.py` imports `yfinance`. If the backtest uses Yahoo Finance data while the live scanner uses IEX, there will be systematic price differences — especially for intraday open prices — that create live/backtest drift. Confirm that all backtest data comes from the same Alpaca IEX source as the live scanner.

- **`eval_checkpoint.json` not in repo**: The 25-trade evaluation checkpoint marker is a runtime file. With 7 trades logged and a fresh clone, the checkpoint will auto-baseline at 7 and count from there. If the checkpoint was previously reached on the live machine (unlikely, only 7 trades), this review won't know.

- **No unit tests**: There are no tests for `risk.calculate_position_size()`, `scanner.evaluate_symbol()` signal logic, or `position_tracker` serialization. The `quantcore` indicators library is an external installed package with no version pin visible in `requirements.txt` — a silent update to the library could change RSI calculations without any test failing.
