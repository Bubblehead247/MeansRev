# MeansRev — two fixes: pending-queue double-load guard, and a bot-driven daily status push

Two independent changes to the Mean Reversion bot repo. Do them as separate commits. Read the referenced files before changing anything — the codebase has a lot of hard-won context in comments; match its style (docstrings explain *why*, not just *what*; alerts never allowed to crash trading; state changes saved before side effects, not after).

---

## 1. Guard `_load_pending()` against double-loading

**Background:** `meansrev_main.py` keeps a module-level `_pending: list[dict]` queue (line ~61), mirrored to `pending.json` so a restart between the post-close scan and the pre-open execute can't lose queued signals. `_load_pending()` (line ~103) restores it from disk with `_pending.extend(payload["actions"])` — extend, not replace.

That's only safe because the two real callers each call it exactly once per process: `main()` at startup (line ~573) for the long-running loop, and `run_one_job()` (line ~676) for the Windows Task Scheduler single-job entry points. Both the loop's `_loop_job()` (line ~651) and a comment at line ~654 explicitly warn about this:

> `_load_pending` extends rather than replaces, so reloading here would duplicate every queued action.

On 2026-08-05, a debug session called job functions directly against live state files instead of going through those two entry points, and called `_load_pending()` more than once in the same process. Whatever was still sitting in `pending.json` (a `DIA EXIT`) got replayed multiple times — several duplicate "Trade logged" lines and multiple `send_review_needed` ntfy pages fired before it self-resolved. No bad order actually went out and no bad row landed in `trades.csv`, but it should not have been possible to get that far.

**Fix:**

1. In `_load_pending()`, before doing anything else, check `if _pending:`. If the in-memory queue is already non-empty, do **not** extend it. Log a `logger.error(...)` that says plainly: the queue was already loaded once this process, refusing to extend it with what's on disk, and that whoever is calling this should restart the process instead of calling `_load_pending()` again. Then `return`.
2. Update the comment at line ~654–656 (in `_loop_job`'s docstring) to point at this guard instead of just describing the danger in prose.
3. Add a test to `tests/test_job_cli.py`, next to the existing `test_the_loop_does_not_reload_the_pending_queue` (line ~199). New test: seed `main._pending` with one action, call `main._load_pending()` (not mocked) against a `pending.json` fixture containing a different action, and assert `main._pending` still has exactly the one seeded action — i.e., the second call was a no-op — and that it logged an error. Follow the existing fixture patterns in that file (`_open_market`, `_no_alerts`, monkeypatching module globals) rather than inventing a new setup style.

**Do not** change the two legitimate call sites (`main()`, `run_one_job()`) or the loop's refusal to call `_load_pending()` at all (`_loop_job` at line ~651) — those are already correct. This is purely a defensive guard inside `_load_pending()` itself.

## 2. Add a daily status push, driven by the bot itself

**Goal:** on every trading day, right after the post-close scan, push one ntfy notification with: account value, today's P&L ($ and %), total P&L ($ and %) since the account's inception, and every open position with its unrealized P&L. This must be generated by the bot's own scheduled job — not by an external script — using the same Alpaca client and ntfy topic the bot already uses for every other alert.

**Where it plugs in:** `status_report()` in `meansrev_main.py` (line ~498) already runs on the same schedule slot as the post-close scan (`schedule.every().day.at(config.SCAN_TIME).do(_loop_job, "status")`, line ~583) and already opens with `if _skip_if_closed("STATUS"): return` — so it already only runs on real trading days (weekdays *and* not a market holiday, per `executor.is_trading_day_today()`). Add the push as a new step inside this function rather than creating a new job/schedule entry — there's no reason to duplicate the trading-day guard or the schedule slot.

**Steps:**

1. **`executor.py`** — add a small account-snapshot helper next to the existing `get_equity()` (line ~49). Something like:

   ```python
   from alpaca.trading.requests import GetPortfolioHistoryRequest  # add to the existing import block, line ~19-25

   def get_account_snapshot() -> dict:
       """Equity, prior-day equity, and since-inception baseline, in one call."""
       account = _client.get_account()
       history = _client.get_portfolio_history(
           GetPortfolioHistoryRequest(period="all", timeframe="1D")
       )
       return {
           "equity":          float(account.equity),
           "last_equity":     float(account.last_equity),
           "base_value":      float(history.base_value),
           "base_value_asof": history.base_value_asof,
       }
   ```

   Reuse `get_alpaca_positions()` (line ~65, already returns `{symbol: position_object}`) for the position list — each `position_object` already has `.qty`, `.avg_entry_price`, `.current_price`, `.unrealized_pl`, `.unrealized_plpc` from alpaca-py. Don't use `position_tracker`'s local state for this — it doesn't carry live price/P&L, only entry-time data.

2. **`notifier.py`** — add `send_daily_status(snapshot: dict, positions: dict)` following the exact shape of every other function in this file (goes through `_push()`, same as `send_checkpoint` / `send_mass_exit_queued`). Priority 3 (routine, not urgent — matches `send_warning`/`send_checkpoint`, not the priority-5 failure alerts), tag `"bar_chart"`.

   Compute inside this function (or pass pre-computed — match whatever's more consistent with how the rest of `notifier.py` divides computation vs. formatting; looking at the file, formatting-only in `notifier.py` and computation in the caller is the existing pattern, so prefer passing already-computed numbers in):

   - Daily P&L $ = `equity - last_equity`; daily P&L % = that / `last_equity` × 100
   - Total P&L $ = `equity - base_value`; total P&L % = that / `base_value` × 100, labelled "since {base_value_asof}"

   Message body, one line per figure, then one line per open position (`SYMBOL | qty sh @ $entry | now $current | +/-$pl (+/-pl_pct%)`), or `"(none)"` if flat. Prefix the title with `[PAPER]` when `config.PAPER` is `True`, so a paper-trading push can never be mistaken for a live one.

   Wrap the actual computation + send in a `try/except` inside `status_report()` (mirroring `_check_for_mass_exit`'s pattern in `meansrev_main.py`, line ~409-412) — a formatting bug or a flaky Alpaca call on this feature must never be able to raise out of `status_report()` and break the rest of the job.

3. **`meansrev_main.py`** — inside `status_report()`, after the existing local-tracker logging block, add the new step: pull `executor.get_account_snapshot()` and `executor.get_alpaca_positions()`, and call `notifier.send_daily_status(...)`, inside the try/except described above. Existing logging behavior in this function (the `pt.all_positions()` loop, the eval-checkpoint check) stays exactly as-is.

4. **Tests** — add to whichever test file already covers `status_report()` (check for one before adding a new file; if none exists, create `tests/test_status_report.py` matching the mocking style used elsewhere, e.g. `tests/test_post_close_scan.py`). Cover:
   - On a non-trading day, no Alpaca calls happen and no push is sent (`_skip_if_closed` short-circuits, same as today).
   - With zero open positions, the push still sends and says "(none)" — this must not be treated as an error path.
   - A raised exception from the Alpaca calls or from `notifier.send_daily_status` is caught and does not propagate out of `status_report()`.
   - The pushed title contains `[PAPER]` when `config.PAPER` is `True`.

**Out of scope — do not touch:** `pending.json`, the execute/confirm jobs, or anything about order submission. This is a read-only reporting feature layered on an existing job slot.
